# 阶段报告 P120：beam search 口径补齐（0A）

**日期**：2026-10-10
**性质**：不重训，从已有 checkpoint 重算口径
**触发**：用户确认「先补 beam search 口径」

---

## Verdict（判答在前）

⚠️ **beam search 在我们当前模型上显著恶化 WER，不是改善。**

**全量 515 条 dev 实测**（checkpoint `p101b-ctrl-last.pt`，ep20，40.0 min）：

| 口径 | WER | 编辑数 | **输出 token 数** | 相对参考长度 |
|---|---|---|---|---|
| **greedy** | **61.86 %** | 1758 | **1892** | **0.67 ×** |
| beam(10) | **125.58 %** | 3569 | **3960** | **1.39 ×** |

分母 = dev 515 条参考 token 总数 **2842**（官方 token 级语料级口径）。
已实测复核：`wer_official(refs, 全部空 hyp)` 返回 `ref_tokens = 2842`，
平均 5.5184 token/句（与 P97 记录的「参考 5.518」一致，互为佐证）。

⇒ **恶化 63.72 pp。**
⇒ ⭐ **核心证据：beam 输出 token 暴涨 109 %（1892 → 3960）**，
   而参考只有 2842 ⇒ **插入彻底失控**，这是 WER 暴涨的直接来源。
   greedy 偏短（0.67×），beam 过长（1.39×），**两个方向都错，beam 更极端**。
⇒ **「官方 42.1% 用 beam 而我们用 greedy，口径吃亏」这个假设被证伪。**
⇒ 相反：**我们应当继续用 greedy**，因为我们模型的概率分布尚未校准到 beam 有利的程度。
⇒ 全部历史数字（60.94% 等）**无需重算**，它们是 greedy 口径下的**最优**数字。

**判活标准**：beam 应 ≤ greedy（beam 是概率上界搜索）。
**实测**：beam 远差于 greedy ⇒ **判死**。

## 二、实现过程中修的 4 个 bug

⚠️ 全部由「已知答案」测试抓出，不是靠肉眼 review。

### bug 1：初始状态错 → beam 恒为空
```python
beam = {(): [NEG, NEG]}   # ❌ 空前缀概率应为 1（log 0）
beam = {(): [0.0, NEG]}   # ✅
```
**症状**：`max() iterable argument is empty`

### bug 2：概率覆盖而非累加
```python
if cand > slot[1]: slot[1] = cand          # ❌ 静默丢路径
slot[1] = _logadd(slot[1], base + v)       # ✅ 多路径汇聚必须累加
```

### bug 3：topk 近似引入垃圾类（**最关键**）
最初用 `torch.topk(row, 64)` 做加速。实测模型分布：

| 区域 | blank 均值 | 非 blank top1 |
|---|---|---|
| 头部 30 帧 | 0.856 | **0.0193** |
| 尾部 30 帧 | 0.856 | **0.0899** |

每帧 **top5 平均概率仅 0.0029** ⇒ top-64 引入大量 ~1e-4 的垃圾类，
经 `logaddexp` 累加 T 帧后仍能与 blank 路径竞争：

```
greedy = ['新','时间','不','。']                              (4 词)
beam64 = ['新','时间','不','。','10月3号','10%','10月3号',...] (22 词)  ❌
```

⇒ **改为全类扩展**（≈2–4 s/样本，515 条约 25 min，可接受）。
⇒ 教训与 MEMORY 0.3 铁律一致：**加速近似会静默改变结果，必须用真实分布验证**。

### bug 4：`int(tensor([11]))` = 10 而非 11
测试脚本里 `torch.randint(3,14,(1,))` 返回 `tensor([11])`，
`int()` 取**第一个元素**（3）而非 11 ⇒ 随机测试的帧数一直是错的。
必须用 `.item()`。

## 三、测试判据本身也错过一次（重要）

我最初写 T1 为「beam=1 必须 == greedy」，**判据是错的**：

- `greedy` = 逐帧 argmax（**局部**最优）
- `beam=1` = 全局最优**单路径**搜索

例：`greedy=[4,11,5,9,11,9,5,5,0,4]` 会把 `5,5` 合成一个并漏掉 `2`；
而 `beam=1` 给出 `[4,11,5,9,11,9,5,2,4]` 才是概率最优。
⇒ 20 次随机测试里 6 次「不一致」，**是我判据错，不是实现错**。

**改用正确判据**：暴力 DP 计算任意 token 序列的最优对齐 log 概率，
断言 `beam 的路径概率 ≥ greedy 的路径概率`（beam 是上界搜索）。
⇒ **20 次全部通过，0 次违反。**

⚠️ 这是 MEMORY「任何体检脚本先『已知答案』验证判据」的第 N 次应用，
但这次**错的是判据而非脚本**，值得单列。

### 最终 5 项测试全部通过

| # | 测试 | 结果 |
|---|---|---|
| T1 | beam=1 路径概率 ≥ greedy（暴力 DP 复核） | ✅ 20/20 |
| T2 | 路径概率随 beam 宽度单调不减 | ✅ 15/15 |
| T3 | CTC 重复类合并（已知答案构造） | ✅ |
| T4 | 全 blank 帧 ⇒ 空序列 | ✅ |
| T5 | 确定性（同输入两次一致） | ✅ |

## 四、结论：为什么 beam 在我们模型上更差

### 现象（6 条真实 dev 样本）

| T | 参考 | greedy | beam(10) | beam 输出尾部 |
|---|---|---|---|---|
| 309 | 13 | 3 | 3 | — |
| 236 | 9 | 4 | **13** | `0,1,0,1,0,1...` |
| 207 | 6 | 4 | 4 | — |
| 169 | 5 | 4 | **8** | `0,1,0,1` |
| 195 | 6 | 1 | 1 | — |
| 145 | 5 | 3 | **9** | `0,1,0,1,0,1` |

**前几个词 beam 总是对的**（`新/时间/不/。`），**问题全在尾部**。

### ⭐ 全量语料级证据（515 条）

| 口径 | 输出 token | 相对参考（2842） | 编辑数 |
|---|---|---|---|
| greedy | 1892 | **0.67 ×** | 1758 |
| beam(10) | 3960 | **1.39 ×** | 3569 |

编辑数从 1758 涨到 3569（**+103 %**），
与输出 token 的 +109 % 几乎同步
⇒ **恶化几乎全部来自插入（insertion），不是替换错误。**

⚠️ 注意 greedy 本身也偏短（0.67×）⇒ 平均输出长度 **1892/515 = 3.6738**。
P97 记录的「输出长度 3.61」来自**另一个 checkpoint**，两者差 0.06
⇒ **量级一致但不能声称完全吻合**（不同模型、不同期次）。
本轮内部对照（greedy 3.67 vs beam 7.69 vs 参考 5.52）自洽。

| 口径 | 平均输出长度 |
|---|---|
| greedy | **3.67** |
| beam(10) | **7.69** |
| 参考 | **5.52** |

⇒ **两个解码器都在长度上偏，只是方向相反：greedy 偏短、beam 偏长。**
⇒ 换言之**长度校准都没解决**，而 beam 把它放大了。

### 机理

模型在句尾「不确定区」输出的非 blank 概率**是头部的 4.7 倍**（0.0899 vs 0.0193）。
beam search 会忠实地沿这些「相对高分」的垃圾路径延伸，
而 greedy 每帧独立取 argmax，遇到 blank 高的帧就自然停住。

⇒ **beam search 的优势前提是模型概率已校准**。
我们 dev WER 60.94% ⇒ 远未校准 ⇒ beam 只会放大尾部噪声。

⚠️ **此结论对官方同样成立**：若我们的模型达到 42% 水平，
beam 大概率转为正收益。**不能据此说 beam 无用。**

### 与 P109 的一致性

P109 理论评估说「**WER 惩罚幻觉而 BLEU 容忍**」。
本轮是该论断的**第一个实验证据**：
beam 倾向更长输出（插入），而 WER 对插入的惩罚高于删除
（P97 已测：输出长度 3.61 vs 参考 5.518，本就是「偏短」）
⇒ **插入在此模型上直接推高 WER。**

⚠️ **一个必须说清的口径限制**：本实验的**参考序列含粘连词**。
按 MEMORY 0.2，官方计算时**参考与识别两侧都拆开**
（`我/可以支持/你/去/运动/。`(6) → `我/可以/支持/你/去/运动/。`(7)）。
而 **beam 输出不会产生粘连词**（它是逐个类 id 串起来的）。
⇒ 这是 beam 劣势的**次要放大因素**，但**不是主因**
——主因是尾部概率结构（见上表），因为 greedy 同样不长。

## 四·补 收据字段修正（第三类错误：读键名）

第一次全量跑出 `greedy_stats: {}` 空字典。原因：
`evaluate()` 的真实键是 **`edits` / `ref_tokens`**（官方口径）
+ `WER_excl_unk` / `WER_per_sentence` / `exact_rate_pct`（附加诊断），
**不是** `ins` / `del` / `sub` / `n`。

⚠️ 我用 `if k in og` 做了容错，于是**不报错、只静默给空**——
这正是 MEMORY 铁律「读取收据前先核对字段名」的又一次应验。
⇒ 已修正为真实键，并额外统计 **`out_tokens`（输出 token 总数）**——
   那是解释 beam 恶化的直接证据（编辑数暴涨的来源）。

## 五、对全局结论的影响

### 「距官方 X pp」需要重新表述

原表述隐含假设「我们 greedy 吃亏」。**实测相反**：

| 口径 | 我们的 WER | 官方 TFNet |
|---|---|---|
| greedy | **61.86%**（p101b-ctrl 实测） | — |
| beam(10) | **125.58%**（同一 checkpoint） | 42.1 |

⚠️ **同一 checkpoint 内的对比**才成立 ⇒ 上表两行均取 `p101b-ctrl-last.pt`（ep20）。
⚠️ 此前版本在此处写的 greedy 60.94% 是 **P100** 的数字，与本行的 p101b-ctrl 不是同一个 run；
同写「~135%」则来自 smoke2（**20 条**子集，非全量），全量实测是 125.58%。两者均已更正。

⇒ **在当前模型水平下，greedy 是我们的最优口径。**
⇒ 全部历史数字无需重算，**且它们已是乐观值**（分母是自己的最优解码）。
⇒ 与官方的差距（15.84 pp，按历史最优 60.94 计）在 greedy 口径下计算，**是偏小的**（对我们有利的一侧）。

### 但要注意的推论

⚠️ 官方模型达到 42.1% 时用了 beam。
⇒ **「同架构下官方 45.1(VAC) vs 我们 60.94」这个对比不完全同口径。**
⇒ 严格做法是等我们模型更强时再重算 beam。
⇒ **但这不改变主结论**：我们与官方的差距是**训练策略与复现质量**问题
（P122 发现 4：官方全部架构改进只值 2.8 pp，我们差 15.84 pp，是 5.6 倍），
不是解码口径问题。

## 六、Next decision

1. **hflip 实验**（P119，运行中）—— 官方默认开启，我们历史全部关闭。
   这是比 beam 更可能有收益的差异。
2. **补解混淆实验**（`word_head=0.0 + warmup_ep=3`）—— P101 遗留，归因未定。
3. **beam 暂不重算**，直到模型 WER 明显低于当前水平。
   若未来降到 50% 以下，重新跑 `p120_beam_eval.py` 即可（脚本已就绪）。

### ⭐ 本轮新发现的一个未试方向：长度校准

| | 平均输出长度 | 相对参考 |
|---|---|---|
| greedy | 3.67 | 偏短 **0.67×** |
| beam(10) | 7.69 | 偏长 **1.39×** |
| 参考 | **5.52** | 1.00× |

**两个解码器都偏离，方向相反。** 这说明**问题不在解码器，在模型的长度建模**。

值得试的两个方向（都低成本）：
- **CTC 空白率调节 / 帧率下采样**：直接改变输出长度的时间尺度
- **长度感知的 loss 加权**：对过长/过短序列加惩罚

⚠️ **但 P90 已做过长度惩罚并作废**（当时结论基于错误实现）。
若重做，**必须先核对 P90 的实现是否真的实现了长度惩罚**，
不能因「以前做过」就跳过——也不能因「作废过」就当没做过。

**依据等级**：【间接】CTC 空白率与输出长度的关系是已知机制，
但**本地 19 篇论文中仅 1 篇（ref07）提到 blank**，且是在
SLT back-translation 语境下（"paths going through the blank label"），
**没有一篇把「降 blank 率」当作 CSLR 提升手段来论证**。
⇒ **该方向缺直接文献支撑**，属我推断。
