# 事故报告 — P123 官方补帧把 dev WER 虚高 16.08 pp

日期：2026-10-12 07:2x · 严重度：**高**（差点毁掉 24 h 的实验，并误判方向）
状态：**已定位、已修复、已续训**

---

## 1. 症状

P123（55 轮 + 官方 milestones[35,45] + `--official-pad` + bf16）跑到 ep30 时：

| 指标 | P123 | 同期 P119 | 差 |
|---|---|---|---|
| 训练 CTC | 10.91 | 11.98（ep27） | **正常，甚至更好** |
| **dev WER** | **74.81 %** | 57.14（ep30） | **+17.7 pp（崩）** |

⇒ 训练损失正常下降、dev 指标却不降 ⇒ 典型的 **train/eval 口径不一致**（不是模型问题）。

---

## 2. 根因：解码截断用了错误的时间长度

开了 `--official-pad` 后，样本被补成 `data_len = ceil(T/4)*4 + 12`
（左 6 帧首帧复制 + 右补末帧到 4 的倍数），**模型的有效输出长度按 data_len 算**。

但评估时 `greedy_decode(logp5, tl_len, idx2word)` 传的是 **`true_len`（真实帧数）**：

```python
t = min(_conv_len(int(lens[b])), seq.shape[1])   # lens 来自 true_len
```

⇒ 一方面少截了尾巴（句尾 gloss 被切掉），
   另一方面 left_pad=6 把真内容整体右移，解码窗口对错了位置。

**训练侧是对的**（CTC 用的是模型自己的 `lgt = out[5]`，由 data_len 推出），
所以只有评估崩。

---

## 3. 决定性验证（同一权重，只换截断长度）

诊断脚本 `tools/blank_gov/p123_diag_pad.py`，checkpoint = `p123-official55bf16-last.pt`（ep31），
**全量 dev 515 条 / 参考 token 2842**：

| 口径 | WER |
|---|---|
| A：pad 开 + 截断用 **true_len**（现行，坏） | **74.74 %** |
| B：pad 开 + 截断用 **data_len**（修好） | **58.66 %** |
| C：pad 关 + 截断用 true_len（交叉验证） | 58.87 % |

**Δ(B−A) = −16.08 pp**

✅ A 的 74.74 % 与训练日志里 ep31 记录的 74.74 **完全一致**
⇒ 诊断脚本精确复现了训练时的评估路径，不是另起炉灶的口径。

✅ B ≈ C（58.66 vs 58.87）⇒ 修好后"补帧与否"对结果无实质影响，符合预期。

---

## 4. 修复

`p78_train_official_tfnet.py` 评估段一行：

```python
- hyps += greedy_decode(logp5, tl_len, idx2word)
+ hyps += greedy_decode(logp5, dl, idx2word)     # dl = data_len
```

**为什么这样改是安全的**：无补帧时 `data_len` 与 `true_len` **恒等**
（collate 里两者都 = `v.shape[0]`）⇒ 对 P93 / P100 / P101 / P119 / P121 **完全等价**。

### 🔴 爆炸半径（重要结论：历史数字全部安全）

| 受影响的运行 | 是否需修正 |
|---|---|
| **P123**（唯一开过 `--official-pad` 的正式训练） | ✅ 需要：ep1–31 的 WER **全部作废** |
| p123-smoke（2 轮冒烟） | 无所谓（本来就 100 %） |
| P93 / P94 / P100 / P101a / P101b / P119 / P121 | ❌ **不受影响**（无补帧 ⇒ 两者恒等） |

⇒ **hflip −3.42 pp、bf16 −3.75 pp、beam 判死 等所有历史结论继续有效。**

## 6. 教训（并入 MEMORY 0.3 同源错误族）

| # | 教训 |
|---|---|
| 1 | **改数据侧（collate / 补帧 / 归一化）时，必须同步检查解码与评估侧是否用同一套长度口径** —— 这是 train-serve skew 的新变体：训练对、评估错，损失曲线完全看不出来 |
| 2 | **"训练损失正常"不能证明评估正确**；发现 dev 指标与同期差 >10 pp 时，第一反应应是查口径而不是查模型 |
| 3 | 冒烟测试只跑 2 轮 ⇒ WER 本来就是 100 %，**验证不了任何评估口径**。补帧这种改动必须做「同权重 A/B 对照」才验得出来 |
| 4 | 诊断脚本载入权重**必须用 `strict=True` + 断言键名存在**。我第一版写成 `ck["model"]`（真实键名是 **`model_state`**），`strict=False` 静默没载入 ⇒ 拿到 155 % 的 WER，**差点得出完全相反的结论** |
| 5 | 诊断脚本要**先复现出训练时记录的数字**（本次 A = 74.74 与日志一致），才证明它走的是同一条路径 |
