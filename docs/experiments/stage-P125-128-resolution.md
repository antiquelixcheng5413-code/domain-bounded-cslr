# 阶段报告：P125 / P126 / P128 —— 分辨率方向的复查

- **日期**：2026-10-13
- **触发**：P124 队列全部结束后，GPU 空闲；三个"技巧"效应（hflip / bf16 / 词级头）
  与自监督方向**全部无法复现或判死** ⇒ 瓶颈不在方法层，转向**与官方实现的系统性差异**
- **结论一句话**：支撑我们全程用 160 分辨率的那份依据（P92）**站不住**，
  分辨率重新成为**唯一未被干净验证的重大差异**；P127（224 干净重训）已启动。

## 1. 静态核对：三项一致，从差异清单划掉

| 项 | 官方（源码） | 我们 | 结论 |
|---|---|---|---|
| 主干初始化 | `Net.py:88` `resnet18(pretrained=True)`，VAC 用 2D resnet18 | 直接 `import` 官方 `Net.moduleNet` | ✅ 一致 |
| 归一化 | `DataProcessMoudle.py:405`（CE-CSL 分支）`imgSeq.float() / 127.5 - 1` | `seq.float() / 127.5 - 1.0` | ✅ 一致 |

⚠️ **过程中的一次误判（值得记）**：官方 `videoAugmentation.ToTensor` **不做归一化**
（只 `from_numpy(...).float()`），我一度以为找到"输入值域差 255 倍"的大差异。
真相是真正的归一化在 **`MyDataset.__getitem__` 的每个数据集分支里**。
⇒ 核对必须沿真实数据路径走到底（transform → `__getitem__` → collate → 模型输入）。

## 2. P125：同权重只换评估裁剪尺寸（全量 dev 515）

| 裁剪 | WER | Δ vs 160 |
|---|---|---|
| `CenterCrop(160)` | **55.84 %** | — |
| `CenterCrop(192)` | 59.08 % | +3.24 pp |
| `CenterCrop(224)` | 64.95 % | +9.11 pp |

🔑 **已知答案校验通过**：160 档 = **55.84 %**，与 P123 收据记录值**完全一致**
⇒ 证明诊断脚本走的是与训练相同的代码路径（这是采信任何诊断结果的前提）。

⚠️ **但不能据此判定 224 有害**：模型以 160 训练，192/224 评估引入了
**train-test 空间尺度不匹配**（resnet 末端特征图 5×5 / 6×6 / 7×7）。
那 9.11 pp 既可能是"224 本身有害"，也可能只是"模型没见过这个尺度"。

## 3. 🔴 P92 收据有错误字段，且其结论不可靠

我们**全程用 160** 的依据是 P92（"160 优于 224 5.60 pp"）。复核发现两个问题：

### 3.1 收据内部自相矛盾

```
p92-resolution-ablation.json
  per_epoch : 160 每轮都低于 224（80.23/84.52 → 72.94/80.86）⇒ 160 全胜 6/6
  mean_diff_pp : -5.6
  win_rate_160 : "0/6"        ← 字段名与数据矛盾（实为 224 胜 0/6）
  verdict      : "224_BETTER" ← ❌ 与数据完全相反
```

⇒ **收据的自动判定字段不能盲信**；我差点因为信任 `verdict` 而直接跳过整个分辨率方向。

### 3.2 即便方向对了，结论也站不住

1. **只跑了 6 轮**，且 224 学得更慢：6 轮内 160 降 **7.29 pp**、224 只降 **3.66 pp**
   ⇒ 与自监督"6 轮"那个坑**完全同源**：**用欠训练产物判方向 = 假阴性**
2. **混淆变量**：P92 = 224 **+ bf16**，P91 = 160 + fp32 ⇒ 分辨率与精度同时改变

⇒ **「160 优于 224」这个老依据作废。分辨率重新成为开放问题。**

## 4. P126：10-crop TTA —— 方法缺陷，结果不采信

设计意图：所有 crop 都是 160×160（与训练尺度一致），只换位置 ⇒ 无尺度不匹配。

结果（40 条子集）：center-1-crop 53.57 % vs 10-crop TTA 56.70 % ⇒ **+3.13 pp 更差**。

❌ **方法本身有缺陷，不要采信这个数**：CTC 各视角在时间上不对齐，
对 log-prob 做跨视角平均会**抹平峰值**，这是序列模型上 TTA 的固有问题。
已弃用该方案。

（附带：`mediapipe 0.10.35` 移除了 `solutions` API，手部关键点方案同样作废。）

### 🔑 比分辨率本身更重要的洞察

从 256 裁 160 ⇒ 训练时 `RandomCrop` 的随机范围是 **96 × 96**
从 256 裁 224 ⇒ 官方的随机范围只有 **32 × 32**

⇒ **我们的「训练随机位置」与「测试 CenterCrop 固定位置」之间的不一致，
比官方严重 3 倍**；再叠加"能量重心偏下 29 px"，测试时是在**系统性切掉下部**。

这可能是 10.74 pp 缺口的来源之一，而且它**独立于分辨率数值本身**——
即使 224 重训没有净收益，这个 train-test 位置不一致也值得单独处理。

## 6. 决策：P127 已启动（224 干净重训）

配置与 **P124e 完全一致，只改 `img_size`** ⇒ 可逐轮配对得到分辨率净效应：

```
--tag p127-res224 --module VAC --img-size 224 --amp-bf16
--epochs 20 --total-epochs 20 --word-head 0.0 --mem-budget 5.2e9 --seed 42
```

对照 P124e（160 / bf16 / wh0 / 20 轮 / 无补帧 / seed 42）。

### 判据（预先写死，看到数字即照此办）

配对区间 **ep13–20**（lr 衰减后），n = 8：

| 条件 | 判定 |
|---|---|
| mean ≤ −1.556 pp **且** SNR ≥ 2 **且** 胜率 ≥ 6/8 | ✅ **224 有益**，全项目切换到 224 |
| mean ≤ −1.556 pp 但胜率 5/8 | ⚠️ 强提示，需第二次独立 run |
| \|mean\| < 1.556 pp | ❌ 不可判 ⇒ 分辨率不是瓶颈，转测 `TemporalRescale` |
| mean ≥ +1.556 pp | ❌ **224 有害**，160 保留（但不等于 P92 那套推理） |

成本约 11 h（224 比 160 慢约 1.24 倍，P92 实测）。

## 7. 失败与教训

| # | 教训 |
|---|---|
| 1 | **收据的自动判定字段必须与原始数据对账**（P92 `verdict` 与 `per_epoch` 相反） |
| 2 | **欠训练产物判方向 = 假阴性**——P92（6 轮）与自监督（6 轮）是同一个坑，第二次踩到 |
| 3 | 静态核对要走到 `__getitem__`，只 grep `transform` 会得出反向结论 |
| 4 | CTC 上做跨视角 log-prob 平均会抹平峰值 ⇒ 序列模型的 TTA 不能这么做 |
| 5 | `mediapipe 0.10.35` 无 `solutions` API；改用帧间差分反而更贴合问题 |
