# 阶段报告：P132 —— WER 口径核对（假设被证伪，但排除了一个方向）

- **日期**：2026-10-14
- **动机**：系统性差异清单清空后仍差 10.74 pp ⇒ 怀疑**评估口径**本身不同
- **结论**：**口径差异只有 0.53 pp，不是缺口来源**。假设被证伪，但该排除的已排除。

---

## 1. 从源码发现的疑点

读官方 `Train.py`：

| 位置 | 内容 |
|---|---|
| `Train.py:97` / `:99` | **`validLoader` 与 `testLoader` 的 `batch_size=1`**（只有 `trainLoader` 是 config 的 2） |
| `WER.py:145 WerScore()` | 对 batch 内每个样本**单独**算 WER，返回 `werScoreSum / batchSize` |
| 验证循环 | `werScoreSum += werScore` … `werScore = werScoreSum / len(validLoader)` |

⇒ batchSize=1 时 `len(validLoader)` == 样本数 ⇒
**官方代码最终报的 WER = 每个句子单独算 WER 再算术平均（逐句等权）**。

而本项目一直用的是**语料级**（CE-CSL 论文式 11：总编辑数 / 总参考 token 数），
并且 MEMORY 里明确记着「逐句等权 … **降级为内部诊断**」——
也就是说，我们一直把官方代码实际使用的口径当成了"非官方口径"。

⇒ 假设：若逐句等权显著更低，则 10.74 pp 中有很大一部分只是口径差异。

## 2. 验证结果（P123 best ep39，全量 dev 515）

| 口径 | WER |
|---|---|
| **A 语料级**（我们一直用的） | **55.84 %** |
| **B 逐句等权**（官方代码实际用的） | **55.31 %** |
| 差（A − B） | **+0.53 pp** |

- 🔑 **已知答案校验通过**：A = 55.84，与 P123 收据一致
- 🔑 **自算一致性通过**：逐句累加得到的语料级 = 55.84（edits 1587 / ref 2842），与 A 完全一致
  ⇒ 证明走的是 `official_wer` 的同一条代码路径

⇒ **差 0.53 pp，远不足以解释 10.74 pp 缺口。假设证伪。**

按逐句等权口径，距官方 45.1 % 仍有 **10.21 pp**。

## 3. 过程中的两个附带发现

### 3.1 朴素 `split("/")` 会高估 1.83 pp

| 分词方式 | 语料级 WER |
|---|---|
| 朴素 `ref.split("/")` | 57.67 % |
| `official_wer`（`split_gloss_sequence` + 粘连两侧拆分） | **55.84 %** |

⇒ 官方口径的 gloss 分词与**粘连词两侧拆分**对结果有实质影响（1.83 pp）。
⇒ 这是 MEMORY 0.3「必须走训练/评估实际代码路径」的又一次验证：
我第一版用自己的 `split("/")` 实现，立刻就偏离了。

### 3.2 官方的 test 数字是在 test 上"选"出来的

`Train.py` 的测试分支（`else`，非训练模式）：

```python
bestWerScore = 65535
for i in range(55):
    checkpoint = torch.load("module/bestMoudleNet_%d.pth" % (i + offset))
    ...                       # 在 testLoader 上评估
    if werScore < bestWerScore:
        bestWerScore = werScore
```

⇒ **遍历 55 个 epoch 的 checkpoint，取 test 上 WER 最低的那个作为最终结果。**

⚠️ 这意味着官方报告的 **test** WER 属于「在测试集上选模型」，会系统性偏低。
（dev/valid 数字是训练时正常选 best，不受影响 ⇒ **dev 45.1 与我们的 55.84 是可比的**。）

⇒ 对我们没有直接影响，但读官方表格时要把 dev 与 test 区别对待。
